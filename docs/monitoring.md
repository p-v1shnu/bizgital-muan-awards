# การเฝ้าระวังและแจ้งเตือน (Monitoring)

> **ขอบเขตที่ตกลงกัน:** แจ้งเตือนเมื่อ **เว็บล่ม** เท่านั้น · เข้า **Microsoft Teams** · ใช้ **บริการภายนอกแบบฟรี**
> ยังไม่รวม: error rate, backup ล้มเหลว, ดิสก์เต็ม, S3 ล่ม — ดูข้อ 6 ว่าจะเพิ่มทีหลังยังไง

> **สถานะ:** ฝั่งโค้ดพร้อมแล้ว (ข้อ 1) · ฝั่งบัญชีบริการภายนอกและ Teams **ต้องคนคลิกเอง** (ข้อ 2–3)
> ผมสมัครบัญชีหรือกดปุ่มใน Teams แทนไม่ได้

## 1. สิ่งที่มีอยู่แล้วในระบบ

| กลไก | ทำอะไร | ทำไม่ได้อะไร |
|---|---|---|
| `GET /api/v1/health` | ตอบ `{"status":"ok"}` **หลังจากยิงคำสั่งจริงเข้าฐานข้อมูล** — ถ้า MySQL ตาย จะไม่ตอบ 200 | ไม่ได้ตรวจ S3 และไม่ได้ตรวจว่าหน้าเว็บแสดงผลถูก |
| `GET /api/health` (ฝั่งเว็บ) | บอกว่า process ของ Next.js ยังรับงานอยู่ | **เข้าจากภายนอกไม่ได้** — Caddy ส่ง `/api/*` ทั้งหมดไปที่ backend · ตัวนี้มีไว้ให้ Docker ใช้ภายในเท่านั้น |
| `restart: unless-stopped` | container ที่ **ตาย** จะถูกเปิดใหม่อัตโนมัติ | container ที่ **ค้าง** (ยังไม่ตายแต่ไม่ตอบ) จะไม่ถูกแตะ เพราะมันไม่เคย exit |
| `healthcheck:` ใน compose | ทำให้ `docker compose ps` บอกได้ว่า container ไหนป่วย | **ไม่รีสตาร์ทให้เอง** — Docker Compose ไม่มีค่านี้ (Swarm/Kubernetes มี) |

**ช่องว่างที่เหลืออยู่จริง ๆ คือ:** ถ้าทั้งเครื่องดับ ไม่มีอะไรในเครื่องนั้นบอกใครได้
ตัวเฝ้าจึงต้องอยู่**คนละเครื่อง** — นั่นคือเหตุผลที่ต้องใช้บริการภายนอก

## 2. ตั้งตัวเฝ้าภายนอก

**ที่แนะนำ: [Better Stack](https://betterstack.com/pricing)** — แผนฟรีระบุไว้ว่ามี 10 monitors และมี
**MS Teams integration** รวมอยู่ด้วย

> **ทำไมไม่ใช่ UptimeRobot** ซึ่งเป็นเจ้าที่คนใช้เยอะกว่า: แผนฟรีของเขา
> [ส่งได้แต่อีเมล — webhook อยู่ในแผน Team ขึ้นไป](https://help.uptimerobot.com/en/articles/14498593-webhook-integration)
> ซึ่งไม่ตรงกับที่เลือกไว้ว่าอยากได้เข้า Teams

### 2.1 สร้าง monitor สองตัว

| # | URL ที่ให้ยิง | พิสูจน์อะไร |
|---|---|---|
| 1 | `https://muanawards.com/` | Caddy + TLS + Next.js — คือสิ่งที่คนทั่วไปเห็น |
| 2 | `https://muanawards.com/api/v1/health` | Caddy + NestJS + **MySQL** — จับกรณีที่หน้าเว็บยังขึ้นจากแคช แต่ข้างในตายแล้ว |

**ต้องมีทั้งสองตัว** เพราะหน้าเว็บถูกแคชไว้ 60 วินาที — ฐานข้อมูลตายไปแล้วหน้าแรกยังขึ้นได้อีกพักหนึ่ง
ตัวที่ 2 คือตัวที่จะรู้ก่อน

### 2.2 ค่าที่ควรตั้ง

| ค่า | ตั้งเป็น | เหตุผล |
|---|---|---|
| ความถี่ | 1–3 นาที | ต่ำกว่านี้ไม่ได้อะไรเพิ่ม เว็บนี้ไม่ใช่ระบบซื้อขาย |
| แจ้งเตือนเมื่อพลาดกี่ครั้ง | **2 ครั้งติด** | ครั้งเดียวอาจเป็นเน็ตกระตุก — เตือนผิดบ่อย ๆ แล้วคนจะเลิกสนใจ ซึ่งอันตรายกว่าไม่มีระบบเตือน |
| Expected status | `200` | |
| Keyword ที่ต้องเจอในหน้า (ตัวที่ 2) | `ok` | กันกรณีตอบ 200 แต่เนื้อในเป็น error |
| Request timeout | 10–15 วินาที | |

> **ไม่ต้องห่วงเรื่องโดนบล็อก** — ระบบจำกัดที่ 100 ครั้ง/นาที ต่อ 1 IP
> ยิงทุก 1 นาทีจากหลายภูมิภาค อยู่ห่างจากเพดานมาก

## 3. ต่อเข้า Microsoft Teams

> ⚠️ **เรื่องที่เพิ่งเปลี่ยนและต้องรู้:** "Incoming Webhook" แบบเดิมของ Teams (Office 365 Connectors)
> [ถูกปิดไปแล้วช่วง 18–22 พ.ค. 2026](https://devblogs.microsoft.com/microsoft365dev/retirement-of-office-365-connectors-within-microsoft-teams/)
> ถ้าเจอคู่มือเก่าในเน็ตที่บอกให้ไป "Connectors → Incoming Webhook" **นั่นใช้ไม่ได้แล้ว**

### ทางที่ 1 — ใช้แอป Better Stack ใน Teams (ง่ายกว่า)

ตาม [คู่มือของเขา](https://betterstack.com/docs/uptime/microsoft-teams/): ติดตั้งแอป Better Stack จาก
Teams app store → เลือกทีม → กดลิงก์เชื่อมบัญชี → อนุญาตสิทธิ์

**ข้อควรระวัง:** เป็นการติดตั้งแอปของบุคคลที่สามเข้า tenant — องค์กรจำนวนมากตั้งค่าให้ต้องได้รับ
อนุมัติจากผู้ดูแล M365 ก่อน ถ้าติดตรงนี้ให้ไปทางที่ 2

### ทางที่ 2 — Power Automate Workflow (ถ้าติดตั้งแอปไม่ได้)

เป็นวิธีที่ Microsoft แนะนำให้ใช้แทน webhook เดิม และไม่ต้องติดตั้งแอปภายนอก

1. ใน Teams กด **…** ข้างชื่อ channel → **Workflows**
2. เลือกเทมเพลต **“Post to a channel when a webhook request is received”**
3. จะได้ URL มาหนึ่งอัน — **URL นี้คือรหัสผ่าน** ใครมีก็โพสต์เข้า channel ได้ อย่าเอาไปวางในที่สาธารณะ
4. เอา URL ไปใส่ใน Better Stack เป็น **Webhook integration**

## 4. ทดสอบว่าเสียงเตือนดังจริง — ห้ามข้าม

**ระบบเตือนที่ไม่เคยถูกทดสอบ ไม่ต่างจากไม่มี** ให้ทำทันทีหลังตั้งเสร็จ:

```bash
# บนเซิร์ฟเวอร์ — ปิด API ทิ้งไว้ 3 นาที
docker compose stop backend

# ...รอให้ข้อความเด้งเข้า Teams แล้วค่อยเปิดคืน
docker compose start backend
```

ถ้า **3 นาทีแล้วไม่มีอะไรเด้ง** แปลว่าตั้งไม่สำเร็จ — อย่าเพิ่งปล่อยผ่าน
และควร **ซ้อมซ้ำทุก 6 เดือน** เพราะ token และสิทธิ์ต่าง ๆ หมดอายุเงียบ ๆ ได้

## 5. เมื่อเสียงเตือนดังตอนตีสาม — ทำอะไรตามลำดับ

```bash
ssh <user>@<server>
cd /path/to/bizgital-muan-awards

docker compose ps          # ← เริ่มที่นี่เสมอ ดูว่าตัวไหน exited หรือ unhealthy
```

| สิ่งที่เห็น | แปลว่า | ทำ |
|---|---|---|
| ทุกตัว `Up (healthy)` | เว็บไม่ได้ล่ม — ปัญหาอยู่ที่ DNS / Caddy / ใบรับรอง | `systemctl status caddy` แล้ว `journalctl -u caddy -n 50` |
| `backend` เป็น `unhealthy` | process ค้าง | `docker compose logs backend --tail 100` แล้ว `docker compose restart backend` |
| `mysql` ไม่ขึ้น | ฐานข้อมูลไม่ยอมสตาร์ท | `docker compose logs mysql --tail 100` — เช็ก `df -h` ด้วย ดิสก์เต็มทำให้ MySQL ไม่สตาร์ท |
| ทุกตัวหายหมด | เครื่องรีบูต | `docker compose up -d` |

**เช็กดิสก์ทุกครั้ง** — `df -h` · สาเหตุที่พบบ่อยที่สุดของเว็บล่มเงียบ ๆ บนเซิร์ฟเวอร์เล็กคือดิสก์เต็ม
(log ถูกจำกัดไว้ที่ 10 MB × 3 ไฟล์ต่อ container แล้ว แต่ไฟล์สำรองข้อมูลไม่ได้ถูกจำกัด)

ถ้าแก้ไม่ได้ใน 15 นาที และงานกำลังจะเปิดรับสมัคร — ปิดฟอร์มรับสมัครไว้ก่อนดีกว่าปล่อยให้คนกรอกแล้วข้อมูลหาย

## 6. สิ่งที่ยังไม่ได้เฝ้า และควรเพิ่มเมื่อไหร่

| ยังไม่เฝ้า | ผลถ้าไม่มี | ควรเพิ่มเมื่อ |
|---|---|---|
| **การสำรองข้อมูลล้มเหลว** | นึกว่ามี backup อยู่ ถึงเวลากู้จริงถึงรู้ว่าไฟล์ล่าสุดคือสามเดือนก่อน | **ทันทีที่มีข้อมูลจริงของปี 2026** — ความเสี่ยงสูงสุดในตารางนี้ |
| **500 พุ่งผิดปกติ** | เว็บ "ขึ้น" แต่คนกดส่งรายชื่อไม่ได้ ตัวเฝ้าไม่รู้เรื่อง | ช่วงเปิดรับสมัคร ซึ่งเป็นช่วงที่คนเข้าเยอะที่สุด |
| **ดิสก์ใกล้เต็ม** | ล่มแบบเงียบ ๆ กลางดึก | พร้อมกับข้อบน |
| **S3 / รูปภาพล่ม** | หน้าเว็บขึ้นครบแต่รูปหายหมด | หลังเปิดตัว |
| **ใบรับรอง TLS ใกล้หมดอายุ** | ความเสี่ยงต่ำ Caddy ต่ออายุเองอัตโนมัติ | แผนฟรีของ Better Stack ไม่รวม SSL monitoring — ปล่อยไว้ได้ |

ทั้งหมดนี้ต้องเพิ่มโค้ดฝั่งเซิร์ฟเวอร์ ไม่ใช่แค่ตั้งค่าในหน้าเว็บของบริการภายนอก — บอกได้เมื่อพร้อม

## 7. ถ้าอยากให้มันรีสตาร์ทเองโดยไม่ต้องมีคนลุก

มีวิธี: เพิ่ม container ชื่อ `autoheal` ที่คอยดู container ที่เป็น `unhealthy` แล้วสั่งรีสตาร์ทให้

**แลกกับ:** ต้องให้ container นั้นเข้าถึง Docker socket ของเครื่อง ซึ่งเท่ากับให้สิทธิ์ระดับ root
บนเครื่องนั้นทั้งเครื่อง · สำหรับเว็บที่คนเข้าหลักพัน ผมคิดว่า **ยังไม่คุ้ม** — แจ้งเตือนแล้วคนกดรีสตาร์ท
เพียงพอ และดีกว่าตรงที่มีคนได้เห็นว่าเกิดอะไรขึ้นจริง แทนที่จะถูกซ่อนไปด้วยการรีสตาร์ทเงียบ ๆ วนไป
