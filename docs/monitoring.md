# การเฝ้าระวังและแจ้งเตือน (Monitoring)

> **ขอบเขตที่ตกลงกัน:** แจ้งเตือนเมื่อ **เว็บล่ม** (ข้อ 2–3) · **การสำรองข้อมูลเงียบไป** (ข้อ 8)
> · **500 พุ่งผิดปกติ** (ข้อ 12) · **ดิสก์ใกล้เต็ม** (ข้อ 13) — สองข้อท้ายเพิ่มเมื่อ 18 ส.ค. 2026
> · เข้า **Microsoft Teams** · ใช้ **บริการภายนอกแบบฟรี**
> ที่ยังไม่เฝ้าคือ TLS ใกล้หมดอายุ ซึ่งตั้งใจปล่อย — ดูข้อ 6

> **สถานะ:** ฝั่งโค้ดพร้อมครบทั้ง 4 อย่าง (ข้อ 1, 8, 12, 13 — รวม endpoint และสคริปต์ที่ตัวเฝ้าต้องยิง/ต้องได้ heartbeat)
> · ฝั่งบัญชีบริการภายนอก, monitor 4 ตัว, heartbeat 2 ตัว และ Teams **ต้องคนคลิกเอง** (ข้อ 2–3)
> ผมสมัครบัญชีหรือกดปุ่มใน Teams แทนไม่ได้

## 1. สิ่งที่มีอยู่แล้วในระบบ

| กลไก | ทำอะไร | ทำไม่ได้อะไร |
|---|---|---|
| `GET /api/v1/health` | ตอบ `{"status":"ok"}` **หลังจากยิงคำสั่งจริงเข้าฐานข้อมูล** — ถ้า MySQL ตาย จะไม่ตอบ 200 | ไม่ได้ตรวจ S3 และไม่ได้ตรวจว่าหน้าเว็บแสดงผลถูก |
| `GET /api/health` (ฝั่งเว็บ) | บอกว่า process ของ Next.js ยังรับงานอยู่ | **เข้าจากภายนอกไม่ได้** — Caddy ส่ง `/api/*` ทั้งหมดไปที่ backend · ตัวนี้มีไว้ให้ Docker ใช้ภายในเท่านั้น |
| `GET /api/v1/health/errors` | บอกว่า **5xx พุ่งขึ้นไหม** ในช่วง 5 นาทีที่ผ่านมา — ตอบ 503 เมื่อเกินเพดาน (ข้อ 12) | ไม่รู้เรื่อง 4xx และไม่รู้ว่าคนกดอะไรอยู่ · ตัวนับอยู่ใน process เดียว รีสตาร์ทแล้วเริ่มใหม่ |
| `restart: unless-stopped` | container ที่ **ตาย** จะถูกเปิดใหม่อัตโนมัติ | container ที่ **ค้าง** (ยังไม่ตายแต่ไม่ตอบ) จะไม่ถูกแตะ เพราะมันไม่เคย exit |
| `healthcheck:` ใน compose | ทำให้ `docker compose ps` บอกได้ว่า container ไหนป่วย | **ไม่รีสตาร์ทให้เอง** — Docker Compose ไม่มีค่านี้ (Swarm/Kubernetes มี) |

**ช่องว่างที่เหลืออยู่จริง ๆ คือ:** ถ้าทั้งเครื่องดับ ไม่มีอะไรในเครื่องนั้นบอกใครได้
ตัวเฝ้าจึงต้องอยู่**คนละเครื่อง** — นั่นคือเหตุผลที่ต้องใช้บริการภายนอก

## 3. ต่อเข้า Microsoft Teams

> ⚠️ **เรื่องที่เพิ่งเปลี่ยนและต้องรู้:** "Incoming Webhook" แบบเดิมของ Teams (Office 365 Connectors)
> [ถูกปิดไปแล้วช่วง 18–22 พ.ค. 2026](https://devblogs.microsoft.com/microsoft365dev/retirement-of-office-365-connectors-within-microsoft-teams/)
> ถ้าเจอคู่มือเก่าในเน็ตที่บอกให้ไป "Connectors → Incoming Webhook" **นั่นใช้ไม่ได้แล้ว**

### ทางที่ 1 — ใช้แอป Better Stack ใน Teams (ง่ายกว่า)

ตาม [คู่มือของเขา](https://betterstack.com/docs/uptime/microsoft-teams/): ติดตั้งแอป Better Stack จาก
Teams app store → เลือกทีม → กดลิงก์เชื่อมบัญชี → อนุญาตสิทธิ์

**ข้อควรระวัง:** เป็นการติดตั้งแอปของบุคคลที่สามเข้า tenant — องค์กรจำนวนมากตั้งค่าให้ต้องได้รับ
อนุมัติจากผู้ดูแล M365 ก่อน ถ้าติดตรงนี้ให้ไปทางที่ 2

### ทางที่ 2 — Power Automate Workflow (ถ้าติดตั้งแอปไม่ได้)

เป็นวิธีที่ Microsoft แนะนำให้ใช้แทน webhook เดิม และไม่ต้องติดตั้งแอปภายนอก

1. ใน Teams กด **…** ข้างชื่อ channel → **Workflows**
2. เลือกเทมเพลต **“Post to a channel when a webhook request is received”**
3. จะได้ URL มาหนึ่งอัน — **URL นี้คือรหัสผ่าน** ใครมีก็โพสต์เข้า channel ได้ อย่าเอาไปวางในที่สาธารณะ
4. เอา URL ไปใส่ใน Better Stack เป็น **Webhook integration**

## 4. ทดสอบว่าเสียงเตือนดังจริง — ห้ามข้าม

## 5. เมื่อเสียงเตือนดังตอนตีสาม — ทำอะไรตามลำดับ

```bash
ssh <user>@<server>
cd /path/to/bizgital-muan-awards

docker compose ps          # ← เริ่มที่นี่เสมอ ดูว่าตัวไหน exited หรือ unhealthy
```

| สิ่งที่เห็น | แปลว่า | ทำ |
|---|---|---|
| ทุกตัว `Up (healthy)` | เว็บไม่ได้ล่ม — ปัญหาอยู่ที่ DNS / Caddy / ใบรับรอง | `systemctl status caddy` แล้ว `journalctl -u caddy -n 50` |
| `backend` เป็น `unhealthy` | process ค้าง | `docker compose logs backend --tail 100` แล้ว `docker compose restart backend` |
| `mysql` ไม่ขึ้น | ฐานข้อมูลไม่ยอมสตาร์ท | `docker compose logs mysql --tail 100` — เช็ก `df -h` ด้วย ดิสก์เต็มทำให้ MySQL ไม่สตาร์ท |
| ทุกตัวหายหมด | เครื่องรีบูต | `docker compose up -d` |

**เช็กดิสก์ทุกครั้ง** — `df -h` · สาเหตุที่พบบ่อยที่สุดของเว็บล่มเงียบ ๆ บนเซิร์ฟเวอร์เล็กคือดิสก์เต็ม
(log ถูกจำกัดไว้ที่ 10 MB × 3 ไฟล์ต่อ container แล้ว แต่ไฟล์สำรองข้อมูลไม่ได้ถูกจำกัด)

ถ้าแก้ไม่ได้ใน 15 นาที และงานกำลังจะเปิดรับสมัคร — ปิดฟอร์มรับสมัครไว้ก่อนดีกว่าปล่อยให้คนกรอกแล้วข้อมูลหาย

## 7. ถ้าอยากให้มันรีสตาร์ทเองโดยไม่ต้องมีคนลุก

มีวิธี: เพิ่ม container ชื่อ `autoheal` ที่คอยดู container ที่เป็น `unhealthy` แล้วสั่งรีสตาร์ทให้

**แลกกับ:** ต้องให้ container นั้นเข้าถึง Docker socket ของเครื่อง ซึ่งเท่ากับให้สิทธิ์ระดับ root
บนเครื่องนั้นทั้งเครื่อง · สำหรับเว็บที่คนเข้าหลักพัน ผมคิดว่า **ยังไม่คุ้ม** — แจ้งเตือนแล้วคนกดรีสตาร์ท
เพียงพอ และดีกว่าตรงที่มีคนได้เห็นว่าเกิดอะไรขึ้นจริง แทนที่จะถูกซ่อนไปด้วยการรีสตาร์ทเงียบ ๆ วนไป

## 8. เฝ้าการสำรองข้อมูล

`scripts/backup.sh` **ยิงบอกว่าสำเร็จ** ทุกครั้งที่จบด้วยดี ถ้าคืนไหนเงียบ = มีปัญหา

ทำไมถึงเลือกแบบ "เงียบคือผิด" แทนที่จะให้มันร้องตอนพัง — เพราะสคริปต์ที่ร้องตอนพัง
จะ**เงียบสนิท**ในสามกรณีที่แย่ที่สุด: cron ไม่ทำงานเลย · เซิร์ฟเวอร์ดับ · ตัวที่ใช้ร้องพังเอง

### ตั้งยังไง

1. ใน Better Stack สร้าง **Heartbeat** (คนละอย่างกับ Monitor) ตั้งช่วงเวลาที่ยอมให้เงียบได้ = **26 ชั่วโมง**
   — เผื่อไว้จาก 24 ชั่วโมงกันเตือนผิดตอนเวลาเหลื่อม
2. จะได้ URL มา เอาไปใส่ใน crontab:

```bash
0 3 * * *  cd /srv/muan && MYSQL_ROOT_PASSWORD=xxx \
           BACKUP_HEARTBEAT_URL='https://uptime.betterstack.com/api/v1/heartbeat/xxxx' \
           ./scripts/backup.sh >> /var/log/muan-backup.log 2>&1
```

**ไม่ใส่ก็ได้** — สคริปต์ทำงานปกติเหมือนเดิม แค่ไม่มีใครรู้ว่ามันทำงานหรือเปล่า

### สิ่งที่สคริปต์ตรวจให้ก่อนจะยิง

| ตรวจ | จับอะไร |
|---|---|
| `gzip -t` | ไฟล์เสีย อ่านไม่ออก |
| มีตาราง `editions` ในไฟล์ | dump ผิดฐานข้อมูล |
| **ขนาดเทียบกับคืนก่อน** | ข้อมูลหายเกินครึ่ง — ถ้าเจอจะ **ไม่ยิง** และ **ไม่ลบไฟล์ทิ้ง** |

ข้อสุดท้ายเลือกวิธีเทียบกับคืนก่อน ไม่ได้ตั้งเป็นตัวเลขตายตัว เพราะวัดจริงแล้วฐานข้อมูลเปล่า
บีบอัดได้ 2.3 KB ส่วนเว็บวันแรกจริง ๆ (1 ปี 6 หมวด) ได้ 4.0 KB — ตัวเลขตายตัวใดก็ตามจะไปตกอยู่
ผิดฝั่งของสองค่านี้เสมอ

> **ถ้าเพิ่งลบคิวรายชื่อทิ้ง** สคริปต์จะเตือนหนึ่งคืนแล้วคืนถัดไปหายเอง เพราะไฟล์เล็กกลายเป็นค่าอ้างอิงใหม่

### ทดสอบว่ามันดังจริง

ตั้งเสร็จแล้ว **ปิด cron ทิ้งไว้หนึ่งคืน** หรือแก้ URL ให้ผิด แล้วดูว่ามีเสียงเตือนมาไหมหลัง 26 ชั่วโมง

## 9. ผลการทดสอบด้วยการจงใจทำให้พัง

ทำจริงเมื่อ 15 ส.ค. 2026 — ปิดฐานข้อมูล ปิดที่เก็บรูป ปิดตัวเว็บเอง แล้วดูว่าผู้ใช้เห็นอะไร
**เจอของจริง 3 จุด แก้แล้วทั้งหมด**

### สิ่งที่ทดสอบและผลลัพธ์ตอนนี้

| ปิดอะไร | ผู้ใช้เห็นอะไร | สถานะ HTTP |
|---|---|---|
| **ฐานข้อมูล** · หน้าที่เคยมีคนเข้าแล้ว | เนื้อหาเดิมยังขึ้นปกติ (แคช 60 วินาที) | 200 |
| **ฐานข้อมูล** · หน้าที่ยังไม่เคยมีคนเข้า | หน้าขัดข้องภาษาลาว | **503** |
| **ตัวเว็บทั้งตัว** | หน้าขัดข้องภาษาลาว | **502** |
| **ที่เก็บรูป (S3)** | ทุกหน้ายังใช้งานได้ครบ แต่รูปหายหมด | 200 |
| API ระหว่างที่ทุกอย่างพัง | ยังตอบเป็น JSON — ตัวเฝ้าและหลังบ้านอ่านได้ | ตามจริง |

ไม่มีเคสไหน "ค้าง" — ทุกอย่างตอบกลับภายในเสี้ยววินาที

### 3 จุดที่เจอ

1. **หน้าขัดข้องไม่เคยขึ้นเลย** — Next มีหน้า error ภาษาลาวอยู่แล้ว แต่**ไม่ทำงาน**ในกรณีนี้
   (ทดสอบทั้ง `error.tsx` และ `global-error.tsx` แล้ว ไม่ขึ้นทั้งคู่) ผู้ใช้ได้หน้าขาวเปล่ากับคำว่า
   *Internal Server Error* → ย้ายไปให้ Caddy เป็นคนตอบแทน ซึ่งครอบคลุมกรณีที่ตัวเว็บดับทั้งตัวด้วย
2. **ตัวเฝ้าไม่มีทางรู้ว่ารูปหาย** — `/health` ไม่ได้แตะ S3 เลย → เพิ่ม `/api/v1/health/storage` แยกไว้
   (ดูข้อ 10 ว่าทำไมถึงแยก)
3. **ตอนอัปโหลดรูปไม่ได้ ทีมงานเห็นข้อความภาษาอังกฤษของเบราว์เซอร์** (`Failed to fetch`)
   ซึ่งชี้ไปผิดที่ → เปลี่ยนเป็นข้อความลาวที่บอกว่าติดต่อที่เก็บรูปไม่ได้

### ทำซ้ำเองได้

```bash
docker compose stop mysql     # แล้วเปิดหน้าเว็บที่ไม่เคยเข้า → ต้องได้หน้าลาว 503
docker compose start mysql
```

## 11. ตัวเลขที่ตกลงไว้ — เสียหายได้แค่ไหน กู้ต้องเสร็จเมื่อไหร่

ก่อนหน้านี้มีสคริปต์สำรองข้อมูลและซ้อมกู้คืนแล้ว แต่**ไม่มีตัวเลขว่าเท่าไหร่ถึงเรียกว่าพอ**
ซึ่งแปลว่าไม่มีอะไรบอกได้ว่าควรสำรองถี่แค่ไหน ตัวเลขข้างล่างคือข้อเสนอ — แก้ได้ตามที่คุณเห็นควร

| | ตั้งไว้ที่ | มาจากไหน |
|---|---|---|
| **RPO** — ข้อมูลหายได้กี่ชั่วโมง | **24 ชั่วโมง** ปกติ · **12 ชั่วโมง** ช่วงเปิดรับสมัคร | สำรองตี 3 ทุกคืน · ช่วงเปิดฟอร์มข้อมูลไหลเข้าเร็วและ**ไม่มีที่อื่นเก็บสำรองเลย** เพราะคนส่งไม่ได้ล็อกอิน ไม่มีทางตามกลับ |
| **RTO** — กู้ต้องเสร็จใน | **15 นาที** ถ้า container พัง · **4 ชั่วโมง** ถ้าทั้งเครื่องหาย | อย่างแรกคือรีสตาร์ท อย่างหลังคือสร้างเครื่องใหม่ + `docker compose up` + restore |
| **เป้าหมายความพร้อมใช้งาน** | **99%** ต่อเดือน (ล่มได้ ~7 ชม./เดือน) | เว็บให้ข้อมูล ไม่ใช่ระบบซื้อขาย · ล่มตอนตีสามไม่เท่ากับล่มตอนประกาศผล |
| **วันประกาศผล** | ไม่ควรล่มเลย | คนเข้าพร้อมกันมากที่สุด และเป็นวันเดียวในรอบปีที่พลาดไม่ได้ |

### สิ่งที่ต้องทำเพิ่มจากตัวเลขข้างบน

- **ช่วงเปิดรับสมัคร ให้เพิ่ม cron เป็นวันละ 2 รอบ** (ตี 3 และบ่าย 3) แล้วปรับกลับเมื่อปิดฟอร์ม
  ```bash
  0 3,15 * * *  cd /srv/muan && ... ./scripts/backup.sh >> /var/log/muan-backup.log 2>&1
  ```
  ถ้าทำแบบนี้ ต้องตั้ง Heartbeat ให้ยอมเงียบได้ **14 ชั่วโมง** แทน 26
- **ก่อนวันประกาศผล ให้สำรองมือเพิ่มหนึ่งรอบ** และอย่าแตะอะไรในระบบวันนั้น

### 4 ชั่วโมงนั้นวัดมาจากอะไร

ซ้อมจริงแล้ว (14 ส.ค.) บนฐานข้อมูลที่มี 10,002 รายชื่อ: dump 868 KB · restore แล้ว
**จำนวนแถวตรงกันทุกตาราง ภาษาลาวไม่เพี้ยน** ตัว restore ใช้เวลาไม่ถึงนาที
เวลาที่เหลือใน 4 ชั่วโมงคือการหาเครื่องใหม่ ตั้ง DNS และรอใบรับรอง TLS ซึ่งเป็นส่วนที่ช้าที่สุด

> **ข้อจำกัดที่ต้องรู้:** ตัวเลข RTO นี้ยังไม่เคยซ้อมแบบ "เครื่องหายทั้งเครื่อง" จริง
> ซ้อมมาแค่ส่วนกู้ฐานข้อมูล · จะรู้ของจริงก็ต่อเมื่อได้ลองสร้างเครื่องใหม่จากศูนย์หนึ่งครั้ง

## 12. เฝ้า 500 ที่พุ่งขึ้น — ความล้มเหลวที่ตัวเฝ้ามองไม่เห็น

ตัวเฝ้าภายนอกยิงหน้าเว็บกับ `/health` แล้วเห็นว่า "ขึ้น" — แต่ทั้งสองอย่างนั้นยังตอบ 200 ได้สบาย
ในขณะที่**ทุกคนที่กดส่งรายชื่ออยู่ได้ 500** เพราะไม่มีใครยิงเส้นทางนั้น

`GET /api/v1/health/errors` คือคำตอบของช่องว่างนั้น: API นับ 5xx ที่ตัวเองส่งออกไป (ทีละนาที ย้อนหลัง 5 นาที)
แล้วตอบตามนี้

| สถานะ | ตอบ |
|---|---|
| ต่ำกว่าเพดาน | `200` · `{"status":"ok","serverErrors":n,"windowMinutes":5,"threshold":10}` |
| ถึง/เกินเพดาน | **`503`** พร้อมข้อความว่ากี่ครั้งในกี่นาที |

### ตั้ง monitor ตัวที่ 4

| ค่า | ตั้งเป็น | เหตุผล |
|---|---|---|
| URL | `https://muanawards.com/api/v1/health/errors` | |
| ความถี่ | **5 นาที** | หน้าต่างที่นับคือ 5 นาที ยิงถี่กว่านั้นก็อ่านหน้าต่างเดิมซ้ำ |
| แจ้งเตือนเมื่อพลาดกี่ครั้ง | 1 ครั้ง | ตัว endpoint นับให้แล้วว่า "หลายครั้ง" จึงไม่ต้องรอซ้ำอีกชั้น |
| Keyword | `ok` | 503 ไม่มีคำนี้อยู่แล้ว — เป็นตาข่ายอีกชั้นถ้าวันหนึ่ง status code เปลี่ยน |

**เพดานตั้งไว้ 10 ครั้ง/5 นาที** แก้ได้ด้วย `ERROR_SPIKE_THRESHOLD` ในไฟล์ env ของ backend
· เลือกเลขนี้เพราะต่ำพอที่เส้นทางบันทึกข้อมูลพังแล้วรู้ภายในไม่กี่นาที และสูงพอที่ crawler ยิง URL เพี้ยนอยู่ตัวเดียวจะไม่ปลุกใคร

### สองข้อที่ตั้งใจออกแบบไว้แบบนี้

- **ตัวนับอยู่ในหน่วยความจำของ process** ไม่ได้เก็บลง DB — ถ้าต้องมีที่เก็บกลางจึงจะมีความหมาย นั่นคือเหตุผลที่จะต้องเพิ่ม Redis
  ซึ่งข้อ 9 ของ PRD ตัดออกไปแล้ว · `docker-compose.yml` รัน backend ตัวเดียว เลขจึงครบอยู่แล้ว
  · **รีสตาร์ท API แล้วตัวนับเริ่มใหม่** ซึ่งถูกต้องสำหรับสิ่งที่เฝ้า: "พุ่งอยู่ตอนนี้หรือเปล่า" และการรีสตาร์ทก็คือวิธีแก้ตามปกติ
- **ตัวตรวจไม่นับตัวเอง** — `/health/*` ทั้งหมดถูกกันออกจากตัวนับ ถ้าไม่กัน `/health/errors` ที่ตอบ 503
  จะบวกเพิ่มให้ตัวเองทุกครั้งที่ถูกยิง แล้วค้างเสียงเตือนไว้เอง · และ `/health/storage` ที่ตอบ 503 ตอนรูปหาย
  ก็จะไปปลุกคนกลางดึก ซึ่งข้อ 10 ตั้งใจไม่ให้เกิด

### ทดสอบว่ามันดังจริง

ระบบไม่มีทางลัดให้ยิง 500 จากข้างนอก (และไม่ควรมี) — วิธีที่พิสูจน์ได้จริงคือลดเพดานลงชั่วคราว

```bash
# ตั้ง ERROR_SPIKE_THRESHOLD=0 ในไฟล์ env แล้ว
docker compose up -d backend
curl -i https://muanawards.com/api/v1/health/errors   # ต้องได้ 503 ทันที เพราะเพดาน = 0
# แล้วคืนค่าเดิม และ up -d อีกครั้ง
```

> ชุดเทสต์หลังบ้านครอบไว้แล้วทั้งสามอย่าง (`backend/test/health.e2e-spec.ts`): 500 จริงจากเส้นทางจริงถูกนับ ·
> 503 ของตัว endpoint เองไม่ถูกนับ · หน้าต่างที่เงียบตอบ `ok` พร้อมตัวเลขที่ใช้ตัดสิน

## 13. เฝ้าดิสก์ — สาเหตุที่พบบ่อยที่สุดของการล่มเงียบ

`scripts/watch-disk.sh` ตรวจ % ที่ใช้ไปของดิสก์ แล้ว **ยิง heartbeat เฉพาะเมื่อยังไม่เต็ม** — เงียบคือผิด
แบบเดียวกับการสำรองข้อมูล (ข้อ 8) และด้วยเหตุผลเดียวกัน

```bash
*/30 * * * *  cd /srv/muan && DISK_HEARTBEAT_URL='https://uptime.betterstack.com/api/v1/heartbeat/yyyy' \
              ./scripts/watch-disk.sh >> /var/log/muan-disk.log 2>&1
```

ใน Better Stack สร้าง **Heartbeat** อีกตัว ตั้งช่วงที่ยอมให้เงียบได้ **90 นาที** (เผื่อจาก 30 นาที × 3 รอบ)

| ค่า | ค่าเริ่มต้น | หมายเหตุ |
|---|---|---|
| `DISK_WARN_PERCENT` | `85` | เหลือที่พอให้รู้ตัวและแก้ทัน · MySQL ต้องมีที่ว่างแม้แต่จะ**สตาร์ท** ไม่ใช่แค่ทำงาน |
| `DISK_WATCH_PATHS` | `/` | เว้นวรรคคั่นได้หลาย path · ถ้ามีโฟลเดอร์ backup (`BACKUP_DIR`) อยู่จริง สคริปต์เติมให้เอง เพราะไฟล์สำรองเป็นส่วนที่**ไม่มีอะไรจำกัดขนาด** |
| `DISK_HEARTBEAT_URL` | ว่าง | ไม่ใส่ก็ทำงานปกติ แค่ไม่มีใครรู้ว่ามันเคยรัน |

**เวลาเต็มจริง log จะบอกพร้อมของที่ควรดูก่อน** — `du` 6 อันดับแรกของ path นั้น ไม่ต้อง ssh เข้าไปหาซ้ำ
· path หลาย path ที่อยู่บนไฟล์ระบบเดียวกันถูกรายงานครั้งเดียว ไม่ใช่สองปัญหา
· heartbeat ที่ยิงไม่ออกเพราะเน็ตสะดุด **ไม่ใช่** ดิสก์เต็ม — สคริปต์เตือนใน log แล้วออกด้วยรหัส 0

### ทดสอบว่ามันดังจริง

```bash
./scripts/watch-disk.sh                        # ปกติ: บรรทัด ok แล้วยิง heartbeat
DISK_WARN_PERCENT=1 ./scripts/watch-disk.sh    # จำลองดิสก์เต็ม: FAILED + du + exit 1 + ไม่ยิง heartbeat
```
ทั้งสองทางถูกรันจริงตอนเขียน (18 ส.ค. 2026) รวมกรณี heartbeat ยิงไม่ออกด้วย
