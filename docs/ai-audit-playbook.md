# คู่มือสั่ง AI ตรวจระบบ — สำหรับคนที่ไม่ได้อ่านโค้ด

> เขียนจากประสบการณ์จริงของโปรเจกต์ Muan Awards (ส.ค. 2026) — ตรวจ 10 รอบ เจอของจริง ~30 จุด
> ทุกข้อในคู่มือนี้มีตัวอย่างจากงานจริงกำกับ ไม่ใช่ทฤษฎี
> **ไฟล์นี้ไม่ผูกกับโปรเจกต์ใดโปรเจกต์หนึ่ง** — คัดลอกไปใช้กับงานอื่นได้เลย

---

## 0. ใช้แค่ไหน — อย่าทำเต็มทุกงาน

ตอบ 3 คำถามนี้ แล้วนับจำนวน "ใช่"

1. คนนอกองค์กรเข้าถึงได้ไหม
2. เก็บข้อมูลส่วนตัวของใครไหม
3. ถ้าพัง เสียเงินหรือเสียชื่อเสียงไหม

| จำนวน "ใช่" | ความเข้มที่เหมาะสม |
|---|---|
| 0 | ตรวจว่าใช้งานได้ตามที่สั่ง พอ |
| 1 | + ตรวจตอนระบบผิดปกติ + สำรองข้อมูล |
| 2 | + ความปลอดภัย (OWASP) + ความเป็นส่วนตัว |
| 3 | เต็มรูปแบบตามคู่มือนี้ |

---

## 1. หลักการ 4 ข้อ — ใช้ได้ทุกงาน

### 1.1 กว้างก่อน แล้วค่อยแคบ

สั่งให้ตรวจอิสระก่อนโดย**ไม่ตีกรอบ** แล้วค่อยระบุชื่อกรอบมาตรฐานทีหลัง

> **ทำไม:** กรอบมาตรฐานหาเจอเฉพาะสิ่งที่มันถูกออกแบบมาให้หา
> ในงานจริง 19 จุดแรกที่เจอ **ไม่มีข้อไหนเป็นเรื่องความปลอดภัย** — เป็นฟีเจอร์ที่ทำครึ่งเดียว,
> ปุ่มที่หายไป, หน้าเว็บที่ตอบผิดตอนระบบล่ม · ถ้าเริ่มด้วย OWASP จะไม่เจอสักข้อ

### 1.2 ขอหลักฐาน ไม่ใช่ขอสถานะ

"เสร็จหรือยัง" ได้คำตอบที่ AI เชื่อเองว่าจริง · "ยิงทดสอบให้ดูหน่อย" ได้ความจริง

> **ทำไม:** ในงานจริง AI ตอบว่า "ครบแล้ว" อย่างน้อย 5 ครั้ง และผิดทุกครั้ง
> ไม่ใช่การโกหก แต่เป็นการเช็กจากสิ่งที่จำได้ว่าทำ แทนที่จะไปอ่านข้อกำหนดทีละบรรทัด

### 1.3 เปลี่ยนมุมมองทุกรอบ

นี่คือตัวแปรที่ทำนายว่าจะเจอของหรือไม่ — **ไม่ใช่ชื่อกรอบ**
ตรวจมุมเดิมซ้ำ จำนวนที่เจอจะลดลงเร็วมาก แต่ทุกครั้งที่เปลี่ยนมุม ของใหม่จะโผล่

ลำดับมุมมองที่ใช้ได้ผลจริง:

```
ฟีเจอร์ครบไหม
  → ของที่ "มีครึ่งเดียว" (มีในฐานข้อมูลแต่กรอกไม่ได้ / กรอกได้แต่ไม่ขึ้นเว็บ)
  → ตอนระบบผิดปกติ (เซิร์ฟเวอร์ล่ม / ฐานข้อมูลว่างวันแรก / คนละ timezone)
  → ความปลอดภัย
  → หลายคนใช้พร้อมกัน
  → โหลดหนัก
  → กู้คืนข้อมูล
  → การเข้าถึงสำหรับผู้พิการ
```

### 1.4 ให้คนอื่นมาตรวจงานที่ AI ตัวเดิมทำ

AI ที่ตรวจงานตัวเองมีเพดาน เพราะจุดบอดจะคงเส้นคงวาตลอดเซสชัน

**วิธีที่ทำได้โดยไม่ต้องอ่านโค้ด:** เปิดเซสชันใหม่ ให้ AI ที่ไม่รู้บริบทมาก่อน อ่านเอกสารข้อกำหนด + โค้ด
แล้วสั่งว่า *"หาสิ่งที่คนทำพลาดหรือทำไม่ครบ"* — จะเจอคนละชุด · **ทำก่อนขึ้น production**

## 2. สี่คำถามที่ไม่ต้องรู้โค้ดก็ถามได้

| คำถาม | ได้อะไร | ตัวอย่างจากงานจริง |
|---|---|---|
| **"อะไรที่คุณยังไม่ได้พิสูจน์ด้วยการรันจริง"** | แยก "เชื่อว่าทำงาน" ออกจาก "เห็นว่าทำงาน" | เจอว่า CI ไม่เคยผ่าน, docker ไม่เคยรัน, การอ่าน IP ของผู้ใช้ไม่เคยถูกทดสอบ |
| **"คุณตั้งสมมติฐานอะไรไว้ที่ฉันไม่ได้บอก"** | AI เติมช่องว่างด้วยค่าเริ่มต้นเสมอ และค่าเริ่มต้นมักเอียงไปทางระมัดระวัง | ไม่ได้บอกเรื่อง analytics → AI ใส่แบนเนอร์ขอความยินยอมให้เอง ซึ่งไม่ใช่สิ่งที่ต้องการ |
| **"ถ้าคุณถูกจ้างมาทำลายระบบนี้ จะเริ่มตรงไหน"** | บังคับให้คิดแบบผู้โจมตี แทนคิดแบบคนสร้าง | เจอว่าเดารหัสผ่านได้ 6,000 ครั้ง/ชั่วโมงโดยไม่มีอะไรกั้น |
| **"มีมาตรฐานอุตสาหกรรมอะไรที่ระบบแบบนี้ควรผ่าน"** | ให้ AI เป็นคนลิสต์ แล้วเราเลือก | เป็นที่มาของการตรวจ OWASP + 12-Factor ซึ่งเจอเพิ่มอีก 7 จุด |

## 3. สั่งให้ทำแผนที่การตรวจเฉพาะงานนั้น

แทนที่จะถือลิสต์สำเร็จรูปไปใช้ ให้สั่งตอนเริ่มโปรเจกต์ว่า:

> *"จากระบบนี้โดยเฉพาะ ทำรายการมิติที่ต้องตรวจให้ครบ พร้อมบอกว่าอันไหนสำคัญมาก/น้อยสำหรับงานนี้
> และอันไหนไม่เกี่ยวเลย พร้อมเหตุผล"*

โดยให้ครอบ **8 มิติ** นี้ — ลิสต์จะปรับตามงานเอง แต่ไม่มีมิติไหนหายทั้งก้อน

1. **ความถูกต้อง** — ทำตามที่ตกลงไว้ครบไหม
2. **ความสมบูรณ์ของข้อมูล** — กฎธุรกิจถูกบังคับที่ไหน (โค้ด? ฐานข้อมูล?) ถ้าสองคนทำพร้อมกันยังถูกไหม
3. **ความปลอดภัย** — ใครเข้าถึงอะไรได้ ทำอะไรได้
4. **ความเป็นส่วนตัว / กฎหมาย** — เก็บอะไร นานแค่ไหน บอกผู้ใช้หรือยัง
5. **พฤติกรรมตอนพัง** — เซิร์ฟเวอร์ล่ม / ข้อมูลว่าง / เน็ตช้า ผู้ใช้เห็นอะไร
6. **ประสิทธิภาพและสเกล** — ถ้าข้อมูลโตสิบเท่าจะเป็นยังไง
7. **การดูแลหลังขึ้นระบบ** — สำรองข้อมูล, กู้คืน, รู้ตัวเมื่อพัง, ปิดระบบอย่างปลอดภัย
8. **การส่งมอบ** — ทีมที่ต้องใช้จริงมีคู่มือไหม ภาษาที่เขาอ่านออกไหม

## 4. ชื่อกรอบมาตรฐาน — รู้ชื่อไว้พอ ไม่ต้องรู้รายละเอียด

| ชื่อ | ใช้ตอนไหน |
|---|---|
| **OWASP Top 10** | ทุกระบบที่คนนอกเข้าถึงได้ · เวอร์ชันล่าสุดเปลี่ยนหมวดเรื่อยๆ ให้สั่งว่า "ตรวจตามฉบับปีล่าสุด" และให้ AI ไปเช็กรายการจริงก่อน อย่าให้ตอบจากความจำ |
| **OWASP ASVS** | รุ่นละเอียดของ Top 10 · Top 10 = "รู้ว่ามีอะไร" · ASVS = "เช็กทีละข้อว่าผ่าน" (ระดับ 1 พอสำหรับงานทั่วไป) |
| **Threat modelling (STRIDE)** | หาความเสี่ยงจาก*การออกแบบ* ไม่ใช่จากโค้ด · ในงานจริงทำ**หลัง** OWASP ผ่านหมดแล้ว ยังเจออีก 6 จุด — เพราะมันถามคนละคำถาม: OWASP ถามว่า "โค้ดมีช่องโหว่ไหม" STRIDE ถามว่า "รูปแบบที่ออกแบบไว้เปิดช่องอะไร" |
| **12-Factor App** | ระบบที่ต้อง deploy จริง · ระวัง: เขียนมาสำหรับระบบที่ scale หลายเครื่อง บางข้อจึงเป็น "ตัดสินใจแล้วบันทึกเหตุผล" ไม่ใช่ทำตาม |
| **Core Web Vitals (LCP / CLS / INP)** | เว็บสาธารณะ · สั่งว่า "ทำให้ผ่านทั้งสามตัวบนมือถือเน็ตช้า" |
| **WCAG 2.2 AA** | เว็บสาธารณะ · **เครื่องตรวจอัตโนมัติครอบคลุมแค่ ~30–40%** ที่เหลือต้องคนทดสอบ (คีย์บอร์ด, screen reader) |
| **SLO + error budget** | ตกลงว่าระบบควรใช้งานได้กี่ % ของเวลา แล้วค่อยตั้งระบบเฝ้าระวังตามนั้น |
| **Chaos / failure injection** | จงใจทำให้พัง (ปิดฐานข้อมูล ปิด storage เน็ตช้า) แล้วดูว่าผู้ใช้เห็นอะไร |
| **Soak test** | ยิงต่อเนื่องนานๆ (ต่างจากยิงหนักครั้งเดียว) เอาไว้จับ memory leak |
| **RTO / RPO** | ยอมให้ข้อมูลหายได้กี่ชั่วโมง / กู้คืนต้องเสร็จภายในกี่ชั่วโมง — ตัวเลขนี้เป็นตัวกำหนดว่าควรสำรองข้อมูลถี่แค่ไหน |

## 5. เรื่องที่ต้องเพิ่มตามประเภทงาน

| ประเภท | เพิ่มอะไร |
|---|---|
| **ระบบภายในองค์กร** | ตัด SEO / Core Web Vitals ออกได้ · เพิ่ม: สิทธิ์แบบละเอียดรายฟีเจอร์, การส่งออกข้อมูล, log ว่าใครเปิดดูอะไร |
| **มีการชำระเงิน** | **idempotency** (กดจ่ายซ้ำต้องไม่ตัดเงินสองครั้ง), การกระทบยอด, เก็บหลักฐานธุรกรรมแบบแก้ไม่ได้ |
| **เก็บข้อมูลอ่อนไหว** | เข้ารหัสตอนเก็บ, สิทธิ์รายฟิลด์, log การเข้าถึง, กระบวนการลบตามคำขอ |
| **มีแอปมือถือ** | ทดสอบบนเครื่องจริง, เวอร์ชันเก่าที่ผู้ใช้ยังไม่อัปเดต, สถานะออฟไลน์ |
| **งานประกวด / รับสมัคร** | กติกาและเงื่อนไข: ใครมีสิทธิ์, ตัดสินยังไง, ข้อมูลที่ส่งเข้ามาถูกใช้ยังไง |

## 6. สัญญาณว่าการตรวจเริ่มตื้น

- ตรวจรอบใหม่แล้ว **ไม่เจออะไร ทั้งที่ยังใช้มุมมองเดิม** → เปลี่ยนมุม อย่าเพิ่งสรุปว่าครบ
- AI ตอบว่า "ครบแล้ว" **โดยไม่มีตัวเลขหรือผลรันประกอบ**
- แก้จุดหนึ่งแล้ว **ไม่ได้รันทดสอบทั้งชุดซ้ำ** → การแก้สร้างรอยรั่วใหม่ได้เสมอ
- AI **ตอบจากความจำ**เรื่องมาตรฐาน/เวอร์ชัน/ราคา แทนที่จะไปเปิดดูของจริง

## 7. ลำดับที่แนะนำสำหรับโปรเจกต์หนึ่ง

```
1. ตกลงข้อกำหนดเป็นเอกสาร (PRD) — ให้ AI เขียน แล้วเราอ่านทวน
2. พัฒนา
3. รอบตรวจกว้าง — "ไล่ข้อกำหนดทีละบรรทัดเทียบของจริง"        ← มักเจอเยอะสุด
4. รอบ "ของที่ทำครึ่งเดียว" — มีในฐานข้อมูล → กรอกได้ → ขึ้นเว็บ ครบสายไหม
5. รอบ "ตอนระบบผิดปกติ"
6. รอบกรอบมาตรฐาน — OWASP → 12-Factor → WCAG → Core Web Vitals
7. รอบ "หลายคนใช้พร้อมกัน" + โหลดหนัก
8. ซ้อมกู้คืนข้อมูลจริง (ไม่ใช่แค่มีสคริปต์สำรอง)
9. เซสชันใหม่ตรวจงานเซสชันเดิม                                ← จุดบอดคนละชุด
10. คนจริงรีวิว: สคริปต์ deploy + ข้อความทุกคำที่ผู้ใช้เห็น
11. ขึ้นเซิร์ฟเวอร์จริง แล้วเดินเช็กลิสต์หลัง deploy
```

## 8. ข้อจำกัดที่ต้องยอมรับ

- **AI ตรวจงานตัวเองมีเพดาน** — จุดบอดคงเส้นคงวาตลอดเซสชัน (ดูข้อ 1.4)
- **เครื่องตรวจอัตโนมัติจับได้แค่บางส่วน** — WCAG ~30–40% · ความปลอดภัยยิ่งน้อยกว่านั้น
- **AI ไม่รู้ว่าธุรกิจของคุณรับความเสี่ยงได้แค่ไหน** — เรื่องกฎหมาย ความเป็นส่วนตัว และการแลกได้แลกเสีย ต้องคนตัดสิน · หน้าที่ AI คือบอกทางเลือกและผลที่ตามมาให้ครบ
- **ยังไม่มีอะไรพิสูจน์ได้จริงจนกว่าจะเจอผู้ใช้จริง** — เทสต์ผ่าน 100% ไม่ได้แปลว่าใช้งานได้ดี
