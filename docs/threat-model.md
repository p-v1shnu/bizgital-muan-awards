# Threat model (STRIDE) — 15 ส.ค. 2026

> ต่างจากการตรวจตาม OWASP Top 10 ตรงที่อันนั้นถามว่า *"โค้ดมีช่องโหว่ไหม"*
> อันนี้ถามว่า *"ตัวการออกแบบเปิดช่องอะไรไว้บ้าง"* — เลยเจอคนละชุดกัน
> ที่นี่เจอ **6 จุด แก้แล้วทั้งหมด** และมี **3 จุดที่ตั้งใจรับความเสี่ยงไว้**

---

## สิ่งที่ต้องปกป้อง เรียงตามความเสียหายถ้าหลุด

| # | ของ | ถ้าเสียหายแล้วเป็นยังไง |
|---|---|---|
| 1 | **รายชื่อผู้ชนะก่อนวันประกาศ** | งานพัง กู้ไม่ได้ · ทีมติ๊กผู้ชนะลงฐานข้อมูล **ก่อน** ประกาศเสมอ (PRD §4.1) แปลว่าคำตอบนอนอยู่ในระบบเป็นสัปดาห์ |
| 2 | **คิวรายชื่อที่คนส่งเข้ามา** | มีชื่อ อีเมล เบอร์โทรของคนทั่วไป |
| 3 | **บัญชีผู้ดูแล** | เข้าถึงข้อ 1 และ 2 ได้ทั้งหมด |
| 4 | **เว็บต้องขึ้นในวันประกาศผล** | วันเดียวในรอบปีที่คนเข้าพร้อมกัน |

## คนที่เกี่ยวข้อง

ผู้เข้าชมทั่วไป · คนส่งรายชื่อ (ไม่ต้องล็อกอิน) · คนถือลิงก์พรีวิว · ADMIN · SUPER_ADMIN
· cron ที่สำรองข้อมูล · บริการภายนอก (S3, GA4, ตัวเฝ้าระวัง)

## ไล่ตาม STRIDE

### S — ปลอมตัวเป็นคนอื่น (Spoofing)

| ตรวจอะไร | ผล |
|---|---|
| ลิงก์พรีวิวเดาได้ไหม | ✅ เซ็นด้วยกุญแจของตัวเอง (`JWT_SECRET:preview`) ผูกกับปีเดียว มีวันหมดอายุ และบันทึกว่าใครเป็นคนสร้าง |
| เดารหัสผ่านรัว ๆ | ✅ ผิด 8 ครั้งใน 15 นาที = ล็อก · บันทึกลง audit ด้วย |
| ขโมย token ไปใช้ต่อ | ✅ ทุกคำขอเช็กกับฐานข้อมูลใหม่ — ปิดบัญชีแล้วหมดสิทธิ์ทันที ไม่ต้องรอ token หมดอายุ |
| ปลอมเป็นคนส่งรายชื่อ | ⚠️ **ทำได้ และตั้งใจให้ทำได้** — ฟอร์มไม่ต้องล็อกอิน · ตัวคุมคือทีมต้องอ่านทุกรายการก่อน ไม่มีอะไรขึ้นเว็บเอง |

### T — แก้ของที่ไม่ควรแก้ได้ (Tampering)

| ตรวจอะไร | ผล |
|---|---|
| **ลิงก์อัปโหลดบังคับขนาดไฟล์จริงไหม** | 🔴 **ไม่ — เจอจุดนี้** ดูข้อ 1 ล่าง |
| ติ๊กผู้ชนะเองได้ไหม | ✅ ต้องเป็นแอดมิน และฐานข้อมูลบังคับ 1 หมวด 1 ผู้ชนะ |
| ยัด `javascript:` ลงลิงก์โซเชียล | ✅ กรองทั้งฝั่งเซิร์ฟเวอร์และตอนแสดงผล มีเทสต์คุม |
| อ่านไฟล์ทั้ง bucket ได้ไหม | ✅ read ได้ แต่ list ไม่ได้ — **กลไกต่างกันคนละที่** (แก้ 17 ส.ค. 2026): บน DigitalOcean Spaces จริง `docs/storage-policy.json` ใช้ไม่ได้เลย (`PutBucketPolicy` ตอบ 403 แม้กุญแจสิทธิ์เต็ม) จึงให้สิทธิ์ `public-read` เป็นรายไฟล์แทนใน `storage.service.ts` · MinIO (เครื่องพัฒนา) รองรับไฟล์ policy นี้เต็มรูปแบบ ใช้ตรงใน `docker-compose.local.yml` ได้จริง — พลาดมาก่อนหน้านี้: ค่า default ของเครื่องพัฒนาใช้ `mc anonymous set download` ซึ่งเปิด list ด้วย ไม่ตรงกับที่บรรทัดนี้เคยอ้างว่าทดสอบผ่านแล้ว |

### R — ทำแล้วปฏิเสธได้ (Repudiation)

| ตรวจอะไร | ผล |
|---|---|
| มีบันทึกว่าใครทำอะไร | ✅ ทุกการเปลี่ยนสถานะ + ล็อกอินที่ล้มเหลว + การสร้างลิงก์พรีวิว |
| ลบ log ผ่าน API ได้ไหม | ✅ ไม่มี endpoint ลบหรือแก้เลย |
| **ไฟล์สำรองข้อมูลใครอ่านได้บ้าง** | 🔴 **ทุกคนบนเครื่อง — เจอจุดนี้** ดูข้อ 2 ล่าง |

### I — ข้อมูลรั่ว (Information disclosure)

| ตรวจอะไร | ผล |
|---|---|
| ผู้ชนะรั่วก่อนประกาศ | ✅ กรองที่เซิร์ฟเวอร์ตาม phase · `sitemap`, ระบบแนะนำชื่อ, หน้าโปรไฟล์ กรองด้วยเงื่อนไขเดียวกันหมด |
| ระบบแนะนำชื่อดูดจากคิวไหม | ✅ ไม่ — ดึงจากคลังครีเอเตอร์เฉพาะปีที่เปิดแล้ว |
| **IP ที่เก็บไว้ ย้อนกลับได้ไหม** | 🔴 **เกลือใช้ร่วมกับ JWT_SECRET — เจอจุดนี้** ดูข้อ 3 ล่าง |
| หน้า error หลุด stack trace | ✅ ตอบ `{"statusCode":500,"message":"Internal server error"}` เท่านั้น |
| Swagger เปิดบน production | ✅ ปิดอัตโนมัติ |

### D — ทำให้ใช้งานไม่ได้ (Denial of service)

| ตรวจอะไร | ผล |
|---|---|
| **จำกัด 10 ครั้ง/ชม. ต่อ IP กระทบใครบ้าง** | 🔴 **กระทบคนบริสุทธิ์ — เจอจุดนี้** ดูข้อ 4 ล่าง |
| ข้อความตอนโดนบล็อก | 🔴 **ภาษาอังกฤษ + ป้ายผิด — เจอจุดนี้** ดูข้อ 5 ล่าง |
| ยิงถล่มหน้าเว็บ | ✅ หน้า public แคช 60 วินาที ไม่แตะฐานข้อมูลต่อคำขอ |
| หน่วยความจำรั่ว | ✅ **ยิง 2,105,487 คำขอใน 10 นาที** — RSS 247 MB → 252.7 MB คงที่ |
| ฐานข้อมูลกลับมาแล้ว API ฟื้นเองไหม | ✅ ฟื้นเองใน 5 วินาที ไม่ต้องรีสตาร์ท (ทดสอบแล้ว) |

### E — ยกระดับสิทธิ์ตัวเอง (Elevation of privilege)

| ตรวจอะไร | ผล |
|---|---|
| ADMIN สร้างหรือเลื่อนขั้นเป็น SUPER_ADMIN ได้ไหม | ✅ ทุก endpoint จัดการผู้ใช้เป็น SUPER_ADMIN เท่านั้น |
| ลดขั้นแล้ว token เดิมยังใช้ได้ไหม | ✅ ไม่ได้ — role อ่านจากฐานข้อมูลใหม่ทุกคำขอ ไม่ได้อ่านจาก token |
| สร้าง SUPER_ADMIN คนที่สอง | ✅ API ปฏิเสธ + มีแฟลก `SETUP_ENABLED` เป็นชั้นที่สอง |
| **แชร์กุญแจเดียวกันหลายหน้าที่** | 🔴 **JWT_SECRET ทำ 3 งาน — เจอจุดนี้** ดูข้อ 3 ล่าง |

## 6 จุดที่เจอ และแก้ไปแล้ว

### 1. ลิงก์อัปโหลดไม่บังคับขนาดไฟล์ (T)

ระบบตรวจขนาดตอน**ขอ**ลิงก์ แต่ตัวลิงก์ไม่ได้ผูกขนาดไว้ — **ทดสอบจริง: ขอลิงก์บอกว่า 100 ไบต์
แล้วอัปโหลด 6 MB ผ่านฉลุย** เพดาน 8 MB จึงเป็นแค่คำสัญญาที่เบราว์เซอร์ให้ไว้เอง
ใครได้ลิงก์ไปหนึ่งอันก็ยัดไฟล์ใหญ่เท่าไหร่ก็ได้ ซึ่งแปลว่าค่าเก็บข้อมูลกับค่าเน็ต

**แก้:** ผูก `ContentLength` เข้าไปในลายเซ็น → ทดสอบซ้ำได้ **403** และไฟล์ปกติยังอัปโหลดได้ 200

### 2. ไฟล์สำรองข้อมูลใครก็อ่านได้ (R/I)

ไฟล์ dump มีชื่อ อีเมล เบอร์โทรของทุกคนที่ส่งเข้ามา แต่ถูกเขียนเป็น `644` และโฟลเดอร์ `755`
= ทุก account บนเครื่องอ่านได้

**แก้:** `umask 077` → ตอนนี้ไฟล์เป็น `600` โฟลเดอร์ `700` (ตรวจแล้ว)

### 3. กุญแจดอกเดียวทำสามหน้าที่ (I/E)

`JWT_SECRET` ถูกใช้ 3 อย่างพร้อมกัน: เซ็น token · เซ็นลิงก์พรีวิว · **เป็นเกลือของ IP ที่เก็บไว้**

ปัญหาไม่ใช่ตัวการเข้ารหัส แต่คือ**เหตุผลในการเปลี่ยนมันไม่เหมือนกัน** — วันที่ token หลุด
คุณต้องเปลี่ยน `JWT_SECRET` ภายในชั่วโมงนั้น แล้วมันจะไป**รีเซ็ตการนับ IP ทั้งหมดเงียบ ๆ**
พร้อมกัน คือระบบกันส่งซ้ำและระบบจำกัดจำนวนจะพังกลางเหตุการณ์ที่คุณกำลังแก้อยู่พอดี
และถ้า `JWT_SECRET` หลุด คนที่ได้ไปก็ย้อน IP ทุกแถวกลับได้ด้วย (IPv4 มีแค่ 4 พันล้านค่า ไล่ครบใน
ไม่กี่นาที)

**แก้:** แยกเป็น `IP_HASH_SALT` ของตัวเอง · แอปไม่ยอมสตาร์ทถ้าไม่ได้ตั้ง หรือถ้าตั้งซ้ำกับอีกสองตัว

> ⚠️ **ต้องเพิ่มใน `.env` ก่อน deploy** — `openssl rand -base64 48`

### 4. ที่จำกัด 10 ครั้ง/ชม. ต่อ IP ปิดกั้นคนบริสุทธิ์ (D)

**ทดสอบจริง: คำขอที่ 11 จากที่อยู่เดียวกันถูกบล็อกยาวหนึ่งชั่วโมง**

ที่เป็นปัญหาเพราะ**เครือข่ายมือถือในลาวเอาผู้ใช้จำนวนมากไว้หลังที่อยู่เดียวกัน (CGNAT)** —
"หนึ่ง IP" จึงไม่ได้แปลว่าหนึ่งคน แต่อาจหมายถึงคนทั้งเมือง และฟอร์มเปิดแค่ไม่กี่สัปดาห์ต่อปี
คนที่โดนบล็อกอาจไม่มีโอกาสส่งอีกเลย

**แก้:** ขยายเป็น 30 ครั้ง/ชม. · ยังกันสคริปต์ได้ และตัวคุมสแปมจริง ๆ คือ
ระบบรวมชื่อซ้ำรายวัน + ทีมต้องอ่านทุกรายการก่อนอยู่แล้ว

### 5. ข้อความตอนโดนบล็อกบอกผิดเรื่อง (D)

คนที่โดนเห็น `ThrottlerException: Too Many Requests` พร้อมป้ายว่า `"error":"InternalServerError"`
— ภาษาอังกฤษ เรียกชื่อคลาสในโค้ด และป้ายบอกว่าเซิร์ฟเวอร์พัง ทั้งที่ 429 ไม่ใช่ความผิดของเซิร์ฟเวอร์

**แก้:** ข้อความภาษาลาวที่บอกว่าเกิดอะไรและควรทำยังไง (ลองใหม่ทีหลัง หรือเปลี่ยนเป็น Wi-Fi)
· และแก้ที่ตัวกรอง error ให้ป้ายตรงกับสถานะเสมอ ซึ่งเป็นบั๊กที่กระทบทุก exception ที่สร้างจากข้อความเปล่า

### 6. ป้ายชื่อ error ผิดสถานะทั้งระบบ (D)

ข้อ 5 เป็นอาการ ตัวโรคอยู่ในตัวกรอง error: exception ที่สร้างจาก**ข้อความเปล่า** (ไม่ใช่ object)
จะถูกติดป้าย `InternalServerError` เสมอ ไม่ว่าสถานะจริงจะเป็นอะไร — แก้ที่ต้นทางแล้ว
ป้ายจึงมาจากสถานะเสมอ

## 3 จุดที่ตั้งใจรับความเสี่ยงไว้

| เรื่อง | ทำไมถึงยอมรับ |
|---|---|
| **ใครก็ส่งชื่อเข้ามาได้ ไม่ต้องยืนยันตัวตน** | เป็นการออกแบบตาม PRD · ถ้าบังคับล็อกอินจะไม่มีใครส่ง · ตัวคุมคือทีมอ่านทุกรายการก่อน |
| **เทียบ `REVALIDATE_SECRET` แบบธรรมดา (ไม่ timing-safe)** | เป็นการเทียบสตริงที่ทฤษฎีแล้วจับเวลาได้ · แต่ต้องยิงหลายล้านครั้งผ่านเน็ตเพื่อวัดต่างระดับนาโนวินาที และ endpoint นี้แค่ล้างแคช ไม่ได้อ่านหรือเขียนข้อมูล |
| **แอดมินที่เข้าถึงเซิร์ฟเวอร์ได้ ลบ audit log ได้จากฐานข้อมูลโดยตรง** | จริงสำหรับทุกระบบที่ไม่ได้ส่ง log ออกไปเก็บนอกเครื่อง · ทีมมีไม่กี่คนและรู้จักกันหมด |

## สิ่งที่วิธีนี้ยังไม่ครอบคลุม

- **ไม่ได้ตรวจ dependency** ว่ามีช่องโหว่ที่ประกาศแล้วหรือไม่ — คนละเรื่องกับ STRIDE
- **ไม่ได้ทดสอบเจาะจริง** — นี่คือการอ่านแบบแปลนแล้วหาช่อง ไม่ใช่การลงมือบุก
- **ไม่ได้ครอบคลุมคนใน** ที่ตั้งใจทำผิดและมีสิทธิ์อยู่แล้ว
